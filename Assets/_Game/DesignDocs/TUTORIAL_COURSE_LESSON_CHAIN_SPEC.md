## Authoring Contract

Names are review vocabulary, not final C# API names.

### `TutorialCourseDefinition`

- `schemaVersion`
- stable `courseId`
- positive `courseRevision`
- `lifecycleStatus`: `Active` or `Retired`
- typed host scope: `ProductRouteScope(playableStageId, routeRevisionRange, bounded ordered segment scope)` or `IsolatedValidationFixtureScope(fixtureId, fixtureRevision)`
- `selectionPolicy = StrictLinear`
- `initialEntryId`
- `practiceExitPolicy = ExplicitProceedToChallenge`
- `restartDisposition = RestartWholePlayableStageFromEntry`
- exactly three ordered `TutorialCourseEntryBinding` records
- required course-capability-manifest revision
- `semanticContentDigest`
- separate `presentationContentDigest`

Revision 1 forbids optional entries, branching, random choice, persistent skip, score gates, difficulty forks, and runtime asset discovery.

Only `ProductRouteScope` may be referenced by `PlayableStageDefinition`. `IsolatedValidationFixtureScope` exists solely for contract tests, uses a synthetic non-product P1-A context, and cannot enter catalog, progression, result persistence, reward, or navigation resolution.

### `TutorialCourseEntryBinding`

Common fields:

- stable `courseEntryId`
- positive `entryRevision`
- ordinal `entryIndex`
- `entryKind`: `BasicLesson`, `FreePractice`, or `SummonMasteryChallenge`
- exact `hostSegmentId` within the course definition's bounded segment scope
- exact predecessor entry ID or typed `None`
- exact successor entry ID or typed `Terminal`
- closed `completionEvidenceKind`
- closed entry-presentation arm and exit-presentation arm plus exact P2-B request-definition ID/revision/semantic digest when present
- when presentation is present, frozen request role, ownership-domain set, skip/cleanup policy, continuation shape, and adapter-capability identity/revision
- required capability IDs/revisions
- entry semantic and presentation digests

Entry index and predecessor/successor links must agree. Serialized display order does not drive execution. Revision 1 requires Free Practice and Summon Mastery Challenge to name the same `hostSegmentId`; only the Basic-to-Practice boundary may use a cross-segment handoff.

### `BasicLesson` binding arm

- exact P1-E lesson-plan ID/revision/semantic digest
- exact lesson ID/revision/semantic digest
- presentation ID/revision/presentation digest
- attempt-contract ID/revision/semantic digest
- optional gameplay-reset-policy ID/revision/semantic digest
- required collector-capability digest
- `completionEvidenceKind = ClosedTutorialAttemptCompleted`
- revision-1 P2-B entry/exit presentation arms both typed `None`; P1-E remains the sole Basic presentation owner

`TutorialAttemptOutcome.Completed` alone is insufficient. The gameplay disposition must reach `DispositionSealed`, the presentation step boundary must seal, no retry reservation may remain live, the immutable `TutorialAttemptResult` must exist, and the P1-E current-director course lease must be `FullyReleased` with zero outstanding lesson loans. A legacy intermediate-step transfer cannot open P2-A Practice.

The current first P1-E candidate is Move, not a summon lesson. Renaming or relabelling it cannot satisfy this arm. The summon-block lesson identity remains a fixture decision.

## Identity and Version Rules

The following require a new semantic revision/digest:

- entry membership, kind, order, predecessor, or successor;
- route/segment scope or strict-linear transition policy;
- source P1-E/P1-C/P1-D/P2-A identity or semantic digest;
- P2-B presentation request/handoff identity, request role, ownership domains, skip/cleanup policy, continuation shape, semantic digest, or adapter capability;
- completion-evidence kind, reset disposition, restart disposition, deadline, or capability revision;
- Practice/Challenge variant binding; or
- objective/proof meaning.

Localization, icon, voice/media, explanatory copy, focus treatment, and other nonsemantic display metadata change only the presentation digest. They cannot change request role, ownership, cleanup, skip semantics, continuation, or capability identity.

Course and entry IDs may be retired but never reused. P1-E lesson/proof IDs, P1-D objective IDs, and P2-B course-entry IDs remain separate identity domains.

- transition cleanup clock ID/frequency and positive deadline;
- one canonical `courseSemanticDigest`;
- separate `coursePresentationDigest`; and
- optional full-envelope checksum.

It contains no Unity object, component, mutable asset pointer, scene-object name/path, player progress, runtime generation, reward plan, or final route digest.

Digest construction follows the shared acyclic order:

1. consume the already computed `coreRouteSemanticDigest`;
2. consume exact earlier P1-C encounter-plan/gate digests in fixed spine order;
3. consume the exact earlier P2-A semantic digest or typed absence;
4. compute `courseSemanticDigest` from those inputs plus all P2-B course semantics; and
5. include `courseSemanticDigest` only in the later final `StageRunRouteSnapshot.canonicalDigest`.

The course digest never enters the core, P1-C, or P2-A layer and never includes the final route digest.

Run ID and runtime generations belong only to the envelope checksum, not reusable content identity. An active run never rereads a newer course asset.

## Runtime Identity and Lifecycle

### `TutorialCourseSessionContext`

- `runId`
- runtime-issued `courseSessionId`
- course ID/revision/digests
- monotonically issued `courseGeneration`
- exact `entryCursor = BeforeFirstSelection(Basic entry ID/index, typed no entry generation/selection) | CurrentEntrySelection(entry ID/index, monotonically issued entryGeneration, CourseEntrySelection ID/canonical digest) | BetweenCourseEntries(prior CourseEntryTransitionReceipt ID/canonical digest, successor entry ID/index, successor reservation-state snapshot ID/canonical digest, typed no current entry generation/selection)`
- last transition sequence
- one active transition compare-and-set token
- immutable course snapshot/digest
- current lifecycle state

The route owner compare-and-sets `entryCursor` with the lifecycle transition: initial session admission uses `BeforeFirstSelection`, a successful selection installs `CurrentEntrySelection`, and `Advanced` installs `BetweenCourseEntries` until the successor selection wins. No separate nullable current-entry fields exist. `TutorialCourseCloseContext` is the immutable closure projection of this exact three-arm cursor and must carry identical refs/typed absences.

### Course lifecycle

```text
Unbound
  -> Validating
  -> Ready
  -> BasicActive
  -> BasicClosing
  -> PracticeActive
  -> PracticeClosing
  -> ChallengeActive
  -> OutcomeDelegated
  -> Quiesced
```

Common non-result closure:

```text
any active state
  -> CourseClosing
  -> Released
  or FaultSealed
```

`FaultSealed` is diagnostic evidence. It never means Completed, Clear, mastery, released ownership, disposed run, or unlocked next entry.

### Entry lifecycle

```text
Locked
  -> Available
  -> Selected
  -> Activating
  -> Active
  -> EvidenceFrozen
  -> Closing
  -> Closed
```

Only one entry generation may be Active. A stale callback may report diagnostics but cannot select, activate, close, publish, or affect a later generation.

### `CourseEntrySelection`

- runtime-issued `courseEntrySelectionId`
- run/course/session IDs and generations
- selected entry ID/kind/index and entry generation
- `selectionReason`: `InitialCourseEntry`, `PriorEntryClosed`, or `ProceedToChallenge`
- predecessor transition digest
- monotonic selection sequence
- course semantic digest
- canonical selection digest and checksum

One compare-and-set performs `Available -> Selected`. The initial Basic selection encodes predecessor transition as typed `None`; later selections reference the completed predecessor's canonical transition digest. The canonical selection digest covers its own selection ID, run/course/session and generations, selected entry/kind/index, reason, predecessor digest or typed absence, selection sequence, and course semantic digest. It contains no future transition receipt and excludes the envelope checksum. Double clicks, wrong run/course digest, foreign entry, and stale generation are reject/log-only.

### `PracticeExitSelection`

This is the pre-cleanup latch for an ordinary Practice exit, not a successor-entry selection:

- runtime-issued `practiceExitSelectionId`;
- run/course/session/course-generation and current Practice entry-generation identities;
- exact authorizing current Practice `CourseEntrySelection` runtime ID/canonical digest;
- exact Practice source entry and intended Challenge destination entry;
- `reason = ProceedToChallenge`;
- Basic-to-Practice transition-receipt digest as current traversal provenance;
- monotonic selection sequence and course semantic digest;
- canonical selection digest and checksum.

One compare-and-set changes Practice `Active -> EvidenceFrozen/Closing` and seals this record while Challenge remains Locked. Its canonical digest covers its own selection ID, run/course/session/course and Practice-entry generations, exact authorizing Practice `CourseEntrySelection` ID/digest, exact source/destination entries, reason, current Basic-to-Practice transition digest, selection sequence, and course semantic digest. It contains no successor selection or future transition-receipt digest and excludes the envelope checksum. Duplicate/stale requests return or reference the first winner.

## Evidence and Receipts

### `CourseEntryTransitionReceipt`

Basic and Practice each produce at most one successful transition receipt:

- schema version and run/course/session/generation identities;
- runtime-issued `courseTransitionReceiptId`;
- from/to entry identities;
- source close-selection identity and digest: the P1-E sealed `TutorialAttemptContinuationSelection` for Basic or `PracticeExitSelection` for Practice;
- exact `sourceEvidence = Basic(TutorialAttemptResult ID/canonical digest) | Practice(PracticeSessionResult ID/canonical digest)`;
- closed `segmentBoundaryDisposition`: exactly `SameSegment(hostSegmentId)` or `CrossSegment(segmentEntryReceiptId, segmentEntryReceiptDigest)`;
- fixed owner-evidence slots in this order: P1-E lesson, P1-C execution, P2-A Practice configuration, P2-B entry presentation. Each slot carries owner/type and exactly one closed arm: `Succeeded(runtime ID, canonical digest)`, the slot-specific typed `NotRequiredForEntryKind | NotAuthoredBySnapshot`, or for Practice P2-A exactly `NotAdmittedBySnapshot(all variability/configuration fields absent) | Admitted(NoCallAdmitted | ConfigurationResults[(EnemyVariantConfigurationReceipt ID, canonical digest)] in binding-member then P1-C ticket order)`;
- cleanup watchdog identity and elapsed ticks;
- close sequence;
- fixed disposition `Advanced`;
- canonical `courseTransitionDigest` and envelope checksum.

For Basic, `sourceEvidence` must be `Basic` and name the same immutable result nested by the exact P1-E `TutorialLessonQuiescenceReceipt`; P1-C/P2-A are `NotRequiredForEntryKind`, and P2-B presentation is `NotRequiredForEntryKind` because P1-E owns Basic presentation. For Practice, `sourceEvidence` must be `Practice` and name the same immutable `PracticeSessionResult` whose exact P1-C/P2-A/presentation refs are repeated by the fixed owner slots; P1-E is `NotRequiredForEntryKind`, P1-C must be the exact `EncounterExecutionQuiescenceReceipt(EntryTransition)`, P2-A must match the immutable snapshot as `NotAdmittedBySnapshot` or `Admitted(NoCallAdmitted | complete ordered successful configuration-result coverage)`, and P2-B presentation is `NotAuthoredBySnapshot` or the exact successful current-Practice-selection `StagePresentationResult` whose continuation arm is `GameplayHandoff` with its commit receipt. The source arm must match the source entry and every nested ID/digest must be byte-identical; substitution is a hard fault. `NotAdmittedBySnapshot` is not interchangeable with an admitted lifecycle that happened to receive no call. A configuration failure receipt, cancelled/None presentation result, wrong selection, or missing handoff cannot enter an `Advanced` transition. P2-A configuration rows use binding-member then P1-C ticket ordinal. No revision-1 slot accepts an undefined entry-scoped P2-A close receipt or a raw digest without owner/type/ID.

`courseTransitionDigest` covers the runtime receipt ID, source/destination entries and their exact host segments, generations, the already sealed source-selection digest, the complete source-evidence arm with exact runtime ID/canonical digest, the exact segment-boundary arm, all four fixed owner-evidence slots including typed absences and exact canonical receipt IDs/digests, watchdog identity/ticks, close sequence, and fixed `Advanced` disposition. It excludes constituent envelope checksums and presentation-only copy/media. `SameSegment` is valid only when both entry bindings name the same host segment. `CrossSegment` is valid only for Basic-to-Practice and only when the P1-A receipt names the exact current run/route, source segment, and destination segment and was sealed after successful destination binding. Practice-to-Challenge must use `SameSegment`. Cancel/interruption/fault produces no transition receipt; `TutorialCourseClosureFaultEvidence` plus independent owner rows closes that run path. Only `Advanced` can make the named successor Available.

### Basic source evidence

The Basic transition requires:

- exact closed `TutorialAttemptResult` digest;
- exact authorizing Basic `CourseEntrySelection` ID/digest and course/session/entry generations repeated consistently by the P1-E outcome, result, continuation selection, and lesson-quiescence receipt;
- `TutorialAttemptOutcome.Completed`;
- exact `TutorialGameplayDispositionReceipt` ID/`gameplayDispositionDigest` with `DispositionSealed`;
- exact `TutorialPresentationStepBoundaryReceipt` ID/`presentationStepBoundaryDigest` with `FullyReleased` current-director course ownership and zero outstanding lesson loans;
- zero pending retry reservation; and
- exact continuation identity targeting the Practice entry.

The route owner coordinates one result/continuation compare-and-set. P1-E owns the result; P2-B owns only the exact next-entry selection. No second director callback may advance the legacy enum chain.

### `PracticeSessionResult`

Practice creates lifecycle evidence, not a stage result:

- runtime-issued `practiceSessionResultId`;
- run/course/session/entry IDs and generations;
- P1-C execution instance/generation/content digest;
- exact `practiceP2ACoverage = NotAdmittedBySnapshot(typed absence of variability generation, configuration rows, and entry-scoped close) | Admitted(variabilityGeneration, practiceConfigurationCoverage = NoCallAdmitted | ResultsClosed, entryScopedP2AClose = NotDefinedInRevision1)`, where `ResultsClosed` contains every admitted successful `EnemyVariantConfigurationReceipt` runtime ID/canonical digest in binding-member then P1-C ticket order; any configuration failure means no `PracticeSessionResult`;
- closed `entryPresentationCoverage = NotAuthoredBySnapshot | Succeeded(request ID/generation, StagePresentationResult ID/canonical digest)`;
- fixed terminal reason `ProceedToChallenge`;
- exact canonical P1-C `EncounterExecutionQuiescenceReceipt(EntryTransition)` ID/digest, the closed P2-A admission/configuration and P2-B presentation coverage arms above, and no claim that either run-level P2-A/presentation barrier sealed;
- explicit `NoLearnerProof` marker;
- close sequence, canonical `practiceSessionResultDigest`, and envelope checksum.

`practiceSessionResultDigest` covers the result ID, run/course/session/entry generations, P1-C execution/content and exact EntryTransition receipt, the complete P2-A admission arm with all variability/configuration/entry-close refs or typed absences, the successful current-selection gameplay-handoff presentation coverage or typed not-authored arm, fixed `ProceedToChallenge`, explicit `NoLearnerProof`, and close sequence. It excludes presentation-only metadata and every constituent/result envelope checksum. Cancel, interruption, active restart, or fault produces no `PracticeSessionResult`; the course barrier and independent P1-C/P2-A/presentation run-finalization rows close that path. Omitted, duplicate, misordered, or raw untyped owner evidence faults construction.

Only `ProceedToChallenge` plus every required successful barrier can seal `Advanced`. That receipt changes Challenge `Locked -> Available`; a separate `CourseEntrySelection` compare-and-set then performs `Available -> Selected`. Cleanup fault leaves Challenge Locked.

### `TutorialCourseTraversalFact`

At Challenge terminal delegation, P2-B provides P1-A with scene-reference-free coverage:

- exact P1-A `TerminalFinalizationAuthority` ID/canonical digest;
- course ID/revision/semantic digest;
- canonical Basic and Practice transition-receipt digests;
- exact Challenge `CourseEntrySelection` runtime ID/canonical selection digest and entry generation;
- ordered entry coverage and whether every promised transition closed; and
- explicit absence of course-level outcome/mastery/progress fields;
- canonical `courseTraversalDigest` and envelope checksum.

`courseTraversalDigest` covers the exact terminal-finalization authority, course identity, the canonical Basic/Practice transition digests, exact Challenge `CourseEntrySelection` runtime ID/canonical selection digest/entry generation, ordered coverage, and explicit absence markers. It excludes constituent checksums and presentation-only metadata. P1-D produces the mastery row separately. A UI may derive `course mastered` only from a committed Clear plus the exact achieved objective row. Clear with that row NotAchieved is still a truthful Clear, not course mastery.

### `TutorialCourseCloseContext`

Every course success or fault closure freezes exactly one context arm: `CourseSessionBeforeFirstSelection(Basic stable entry ID, typed no runtime entry generation, typed no CourseEntrySelection) | CurrentEntrySelection(entry ID/ordinal/generation, exact CourseEntrySelection ID/canonical digest and session/course generations) | BetweenCourseEntries(prior CourseEntryTransitionReceipt ID/canonical digest, successor entry ID/ordinal, successor reservation-state snapshot ID/canonical digest, typed no current selection/entry generation)`. The third arm uses the same P1-C `SceneExecutionReservationStateSnapshot` provenance observed immediately before terminalization. The arm, all exact refs, and every typed absence are canonical digest input; a missing session/selection/transition window cannot be inferred from null fields.

### `TutorialCourseClosureFaultEvidence`

- runtime-issued `courseClosureFaultEvidenceId`;
- frozen run/course/session identities and exact `TutorialCourseCloseContext` arm;
- exact close-authority arm/ID/canonical digest: `TerminalFinalizationAuthority`, `ResolvedActiveRunRestartDispatch`, or `StageRunAbortCloseAuthority`;
- last sealed selection/transition as required by that context arm, with typed absence otherwise;
- failed boundary kind;
- cleanup watchdog ticks/deadline;
- pending selection, reservation, work, and handle IDs;
- fixed latest-transition owner-evidence slots in P1-E, P1-C, P2-A, P2-B presentation order: P1-E and P1-C use `NotRequiredForEntryKind | NotReached | Succeeded(exact declared receipt type, runtime ID, canonical digest) | FailedAtCourseTransitionBoundary`; P2-A uses `NotRequiredForEntryKind | NotReached | NotAdmittedBySnapshot | Admitted(NoCallAdmitted | ConfigurationResultsClosed(ordered EnemyVariantConfigurationReceipt IDs/canonical digests in binding-member then P1-C ticket order)) | FailedAtCourseTransitionBoundary`; presentation uses `NotRequiredForEntryKind | NotAuthoredBySnapshot | NotReached | Succeeded(StagePresentationResult runtime ID, canonical digest) | FailedAtCourseTransitionBoundary`; these are only the source-transition slots defined by `CourseEntryTransitionReceipt`, never the independent run-level quiescence barriers;
- fault sequence;
- course semantic digest, canonical `tutorialCourseClosureFaultDigest`, and envelope checksum.

Pending selection/reservation rows use strict course entry ordinal then their issued sequence; work/handle rows use registration sequence; latest-transition slots remain in fixed P1-E, P1-C, P2-A, P2-B presentation order and each successful nested owner coverage uses its canonical internal order. The P2-A configuration array uses the same binding-member/P1-C-ticket keys as its successful transition source and cannot contain a failure receipt. Presentation `NotAuthoredBySnapshot` is legal only when the immutable source-entry snapshot declared no request; `NotReached` is legal only for an authored slot whose trigger or work boundary had not been reached at fault. `FailedAtCourseTransitionBoundary` carries no anonymous receipt; it must match the parent failed boundary, prior slots are successful/no-call/not-admitted/not-authored/not-required as their snapshots require, and later slots are not reached/not-authored/not-required according to the immutable snapshot. Otherwise unowned diagnostics use stable ID ordinal. Duplicate or missing order keys fault. `tutorialCourseClosureFaultDigest` covers the runtime fault-evidence ID, frozen run/course/session provenance, the exact close-context arm and its exact refs/typed absences, exact close authority, last selection/transition canonical digests or typed absence, failed boundary, watchdog facts, canonically ordered pending arrays, every fixed typed latest-transition slot including the complete presentation authored/not-authored distinction and full P2-A admission/configuration arm, course semantic digest, and fault sequence; it excludes presentation-only metadata and every envelope checksum. Before result commit this evidence may attach only to P1-A's one later-sealed `StageRunAbortRecord`. It is never a product result, course result, independent-owner barrier result, persistence input, or reward input.

## Normal Sequence

### Admission

1. P1-A validates route, course, P1-E, P1-C, P1-D, P2-A, and presentation capability identities before mutation.
2. One atomic owner-admission transaction creates the course session, registers all admitted P1-E/course/P1-C/P2-A/presentation barriers, and creates the fixed P1-C binding reservations/latches plus the P2-A acquire-or-close latch only when the snapshot's matching `p2ABinding` arm is `Admitted`, before the run becomes externally active. The P1-E registration starts as `PendingBasicBinding(course/session/generation/stable Basic entry)` rather than fabricating a pre-selection host scope. With `NotAdmittedBySnapshot`, every P2-A lifecycle/generation/configuration field is typed absent. Only Basic becomes Available.
3. Any missing reference, digest disagreement, retired entry, unsupported policy, ownership conflict, or partial registration fails that transaction before an active run/session is exposed; rollback leaves no admitted owner, reservation, latch, work, or `StageRunAbortRecord` gap.
4. The initial selection compare-and-set selects Basic once after the transaction commits and atomically freezes the same P1-E registration as `CourseBasicSelected` with that exact selection ID/digest and entry generation. A competing pre-selection close instead freezes `CourseSessionBeforeBasicSelection` and makes selection permanently illegal. Neither arm exposes a partially rebound barrier.

### Basic

1. P1-E admits the attempt context only from the current sealed Basic `CourseEntrySelection` ID/digest and matching course/session/entry generations, then owns presentation, observation, proof, gameplay disposition, and attempt result.
2. P1-E freezes one terminal outcome and invalidates proof observation.
3. It drains producers and seals gameplay disposition.
4. It seals the presentation step boundary and fully releases the current-director course lease with zero outstanding loans; a transfer-to-next-legacy-step disposition is rejected for this cohort.
5. The route owner contends on P1-E's per-Basic close-publication latch inside the same serialized aggregate as P1-A's global restart latch/version. A normal CAS requires the global latch/version still Open and atomically seals the immutable attempt result, exact Basic-to-Practice continuation, and Basic-authorized `TutorialLessonQuiescenceReceipt`. Restart acceptance atomically wins the global latch and marks an open Basic latch `RestartReserved` before returning; only that arm can seal the suppressed continuation/result/restart-authorized receipt. A restart accepted after `NormalClosed` records typed receipt reuse and cannot rewrite the result.
6. If Basic and Practice name different host segments, P1-A alone validates and dispatches the snapshotted route handoff while Basic remains Closing and Practice remains Locked; successful destination binding seals the exact `StageSegmentEntryReceipt`. If they name the same segment, the transition uses typed `SameSegment` and dispatches no scene load.
7. P2-B validates the closed Basic evidence and exact segment-boundary arm, seals the Basic transition receipt, changes Practice `Locked -> Available`, and only then uses `CourseEntrySelection` to select Practice. It cannot select Practice while the destination is still `HandoffPending`.

Prompt acknowledgement, presentation completion, or `TutorialAttemptOutcome.Completed` without closure cannot open Practice.

### Free Practice

1. An optional entry presentation carries the current Practice `CourseEntrySelection` and must restore/release plus seal a successful `GameplayHandoff` result before P1-C or P2-A runtime admission can win.
2. P1-C creates and owns the frozen nonterminal Practice activity's inactive staging root under a fresh execution generation only after that gate.
3. With `p2ABinding = Admitted`, P2-A first acquires the run-wide Practice/Challenge lifecycle and returns the exact Practice `EnemyVariantConfigurationReceipt`; P1-C validates its receipt ID, ticket, P1-C/P2-A and course-entry generations, authorizing `CourseEntrySelection` ID/digest, snapshot/binding identity, canonical receipt digest, and success disposition. With `NotAdmittedBySnapshot`, P1-C requires `configurationCoverage = NotRequiredBySnapshot` and typed absence of every P2-A generation/call/receipt before activation. P1-C alone arms and activates the root. A missing, stale, failed, foreign, or arm-incompatible receipt/absence rolls back the inactive root and opens no gameplay.
4. The player may issue `ProceedToChallenge`; this is not proof.
5. The P2-B course coordinator seals one `PracticeExitSelection` carrying the exact current Practice `CourseEntrySelection` ID/digest before cleanup begins; Challenge remains Locked.
6. That coordinator sends P1-C the typed close command carrying the exact winning `PracticeExitSelection` ID/digest and awaits P1-C `EntryTransition` cancellation/disposal. When an entry presentation was authored, it revalidates the already sealed current-selection `StagePresentationResult`; it does not close the adapter-level presentation barrier again. It likewise validates fixed P2-A Practice configuration-result coverage but requests no P2-A close. The P1-C success/fault evidence must echo the same exit authority. Neither the run-level `StageVariabilityQuiescenceBarrier` nor `StagePresentationQuiescenceBarrier` seals during this ordinary same-run transition.
7. Only after all required receipts succeed does it seal the Practice result and `Advanced` transition receipt, changing Challenge `Locked -> Available`.
8. A separate `CourseEntrySelection` compare-and-set selects Challenge; only then does Challenge receive a fresh entry/P1-C execution generation.

Practice and Challenge remain inside the same P1-A run. Fresh entry/execution generation is not a new run ID.

### Summon Mastery Challenge

1. An optional entry presentation carries the current Challenge `CourseEntrySelection` and must restore/release plus seal a successful `GameplayHandoff` result before P1-C instance admission or any admitted Challenge entry-scoped P2-A configuration call/activation. With `p2ABinding = Admitted`, the run-wide P2-A lifecycle was already acquired in Practice and remains applied; Challenge does not acquire it again. With `NotAdmittedBySnapshot`, no P2-A lifecycle exists.
2. P1-C creates and owns the Challenge inactive staging root under the new Challenge execution generation only after that gate; P2-B owns neither the root nor activation.
3. With `p2ABinding = Admitted`, P2-A returns the exact Challenge `EnemyVariantConfigurationReceipt`. P1-C validates receipt ID, current ticket, P1-C/P2-A and course-entry generations, authorizing Challenge `CourseEntrySelection` ID/digest, course/variability snapshots, Challenge binding identity, canonical receipt digest, and success disposition before P1-C alone arms and activates the root. With `NotAdmittedBySnapshot`, P1-C instead validates `configurationCoverage = NotRequiredBySnapshot` and complete P2-A absence. Missing, stale, failed, foreign, or arm-incompatible evidence destroys the inactive root, leaves Challenge unactivated, and enters the typed fault path.
4. Once Challenge activates, P2-B has no outcome authority. The run-level P2-A lifecycle remains open only for the admitted arm; the entry configuration receipt is not `StageVariabilityQuiescenceReceipt`. The not-admitted arm registers no P2-A barrier and cannot fabricate a variability generation or receipt.
5. P1-A-owned terminal-subject adapters bound to P1-C-spawned actors submit terminal candidates to P1-A's terminal coordinator. P1-C itself submits only gate/execution facts, and P2-A supplies configuration/provenance only. P1-A alone arbitrates.
6. At terminal finalization, P1-A's terminal arm must first win the shared terminal-or-restart latch and enter `TerminalFinalizing`; only that winner requests frozen course traversal coverage. P2-B seals the coverage and invalidates continuation authority without deciding terminal validity or outcome. P1-A then seals the fixed owner rows in `TerminalFinalizationOwnerCoverageRecord` and enters `TerminalFinalizationOwnersSealed` before `OutcomeFactsSealed`. A later restart is reject-only.
7. Existing authority order remains:

```text
TerminalClosed + terminal-or-restart latch winner
  -> TerminalFinalizing
  -> fact collectors + course traversal/quiescence sealed
  -> P1-C RunFinalization + current-generation presentation aggregate sealed
  -> TerminalFinalizationOwnerCoverageRecord sealed
  -> TerminalFinalizationOwnersSealed
  -> OutcomeFactsSealed
  -> MasteryEvaluating
  -> MasterySealed
  -> [when P2-A is admitted: VariabilityClosing -> VariabilitySealed]
  -> [P1-D/P2-C Clear: PreparationRequested -> PreparationPrepared]
  -> CommitRequested
  -> Committed
  -> [P1-D Clear: ProgressApplying -> ProgressCommitted]
```

8. P1-A owns the Clear/Fail commit. P1-D evaluates the exact objective, then P1-D or P2-C durably prepares the complete Clear handoff before `CommitRequested`; durable Clear application/settlement occurs only after the exact `RunResultCommitReceipt` commits the summary. P2-B writes neither.
9. Fail remains a normal P1-A Fail. The course cannot rewrite it as tutorial interruption or invent a special learner outcome.

## Quiescence

### `TutorialCourseQuiescenceBarrier`

The result is the closed union `Succeeded(TutorialCourseQuiescenceReceipt)` or `Failed(TutorialCourseClosureFaultEvidence)`.

`TutorialCourseQuiescenceReceipt` contains:

- runtime-issued `courseQuiescenceReceiptId`;
- run/course/session identities, invalidated course generation, and exact `TutorialCourseCloseContext` arm with an invalidated entry generation only for `CurrentEntrySelection`;
- exact close-authority arm/ID/canonical digest: `TerminalFinalizationAuthority`, `ResolvedActiveRunRestartDispatch`, or `StageRunAbortCloseAuthority`;
- close reason and exact `courseDisposition = SessionClosedBeforeFirstSelection | CurrentEntryClosed(Transitioned | OutcomeDelegated | Cancelled | Interrupted | ActiveRunRestartRequested) | BetweenEntriesClosed`, matching the close-context arm;
- last sealed `CourseEntrySelection`, `PracticeExitSelection`, and canonical transition digests exactly when required by the context/disposition, with typed absence otherwise;
- for `CurrentEntryClosed`, the canonical `CourseEntryTransitionReceipt` or `TutorialCourseTraversalFact` digest when that disposition requires one; for `BetweenEntriesClosed`, the exact prior transition and terminalized successor-reservation receipt; typed absence for `SessionClosedBeforeFirstSelection`;
- final course lifecycle `Quiesced` or `Released`;
- canonical traversal digest or typed `NotApplicable` for a close before Challenge finalization;
- zero pending selection/transition compare-and-set, continuation reservation, source-evidence token, presentation-request handle, callback, and source-token counts;
- close sequence, canonical `courseQuiescenceReceiptDigest`, and envelope checksum.

The canonical receipt digest covers the receipt ID, exact close authority, course/session provenance, exact close-context and course-disposition arms, exact constituent canonical digests, every typed absence, zero-work facts, and close sequence. It excludes presentation-only metadata and constituent/full-envelope checksums. A post-commit terminal action may only revalidate the already sealed receipt; it cannot reopen the course or replace the original close authority.

Success requires:

- course generation invalidated and, only for `CurrentEntrySelection`, that exact entry generation invalidated;
- zero course-owned pending selection/transition compare-and-set work;
- zero course-owned continuation reservation or unconsumed source-evidence token;
- one matching course disposition sealed: no-entry session close, current-entry close with the exact transition/traversal source digest when applicable, or between-entry close with the prior transition and successor-reservation terminal receipt;
- zero course-owned presentation-request handle;
- ordered traversal coverage sealed when P1-A requested it during Challenge fact finalization, or typed `NotApplicable` for an earlier close; and
- zero course-owned callback/source token.

`TutorialCourseClosureFaultEvidence` accompanies `Failed` and never satisfies success or supplies `courseQuiescenceReceiptDigest`. This barrier neither waits for nor claims a P1-E attempt/retry/gameplay ledger, P1-C object, P2-A modifier/configuration, or P2-B presentation resource. P1-A awaits those independent barriers/results; an external fault cannot be converted into course success.

### `StagePresentationQuiescenceBarrier`

The presentation companion must separately prove:

- every admitted request generation invalidated and playback stopped;
- snapshot-order coverage of every expected slot through an exact trigger-state snapshot and `NotReachedBeforeClose | Admitted`, plus request-admission-order coverage of every admitted `StagePresentationResult`;
- explicit `NoRequestAdmitted` only when the generation snapshot is empty or every expected trigger is proven not reached, under the exact P1-A close authority;
- adapter/work registry empty;
- zero coroutine, task, timer, listener, observer, and frame callback;
- every acquired domain restored/released with receipt;
- no global/additive owner token retained; and
- one aggregate `StagePresentationQuiescenceReceipt` sealed with no stale callback able to reacquire or publish.

A failed pre-commit barrier leads to the one abort record and `ClosureFaulted`. A post-commit dispatch fault preserves the immutable result and uses `StageDispatchClosureFaultRecord`.

### Run-level closure matrix

For a route snapshot that admits this course, P1-A never infers owner closure from a missing instance. P1-E returns `TutorialLessonQuiescenceReceipt` with `NoAttemptStarted` or the exact closed Basic attempt and later reuses that already closed receipt. The course always closes its current session/selection/transition/traversal state through `TutorialCourseQuiescenceReceipt`. The P2-A column below applies only when the frozen matching Practice/Challenge arm is `p2ABinding = Admitted`. With `NotAdmittedBySnapshot`, every row instead uses P1-A owner coverage `NotAdmitted`, and no P2-A latch, generation, close command, barrier result, or receipt exists. The remaining phase-sensitive rows resolve as follows when a run-level close occurs:

| Phase window | P1-C run-finalization arm | P2-A run-finalization arm when admitted | P2-B presentation arm |
|---|---|---|---|
| Course session created / before Basic selection | `NoExecutionStarted(NoBindingForCurrentPhase)` and all reserved binding latches/reservations terminalized | `ClosedWithoutAcquisition(NotIssuedBeforeClose)` | `NoRequestAdmitted` plus every future expected slot `NotReachedBeforeClose` |
| Basic, with or without attempt | `NoExecutionStarted(NoBindingForCurrentPhase)` and all future reservations terminalized | `ClosedWithoutAcquisition(NotIssuedBeforeClose)` | `NoRequestAdmitted` plus Practice/Challenge expected slots `NotReachedBeforeClose` |
| Between Basic `Advanced` and Practice selection | `NoExecutionStarted(BetweenCourseEntries)` with exact Basic transition plus successor Practice reservation and all future reservations terminalized | `ClosedWithoutAcquisition(NotIssuedBeforeClose)` | `NoRequestAdmitted`; Practice/Challenge triggers are not reached |
| Practice Selected / entry presentation / before runtime admission | `NoExecutionStarted(BindingNotYetAdmitted)` with exact Practice selection/binding and all reservations terminalized | close wins `variabilityAcquireOrCloseLatch`, then `ClosedWithoutAcquisition(NotIssuedBeforeClose)` | not-authored slot may remain absent; an authored reached slot carries exact `Succeeded \| Failed \| PendingAtFault` request coverage, or `ReachedButNotAdmitted` only when no request was admitted |
| Practice execution/acquisition active | `ClosedExecution(RunFinalization)` | acquisition won, so normal `Released` | aggregate covers every admitted request in admission order |
| Between Practice `Advanced` and Challenge selection | `NoExecutionStarted(BetweenCourseEntries)` with exact Practice transition plus retained Challenge reservation, then all reservations terminalized | Practice acquisition already won, so normal `Released` | aggregate covers prior requests; the Challenge slot is `NotReachedBeforeClose` |
| Challenge Selected / entry presentation / before runtime admission | `NoExecutionStarted(BindingNotYetAdmitted)` with exact Challenge selection/binding and all reservations terminalized | already acquired run-wide lifecycle closes as `Released` | not-authored slot may remain absent; an authored reached slot carries exact `Succeeded \| Failed \| PendingAtFault` request coverage, or `ReachedButNotAdmitted` only when no request was admitted |
| Challenge execution / terminal finalization | `ClosedExecution(RunFinalization)` | normal `Released` | aggregate covers every admitted request in admission order |

The ordinary same-run Practice close is not a run-finalization row: it consumes `EncounterExecutionQuiescenceReceipt(EntryTransition)`, terminalizes the Practice reservation/lease, and explicitly retains only the unopened Challenge reservation through its canonical reservation-state snapshot. It does not seal the run-level P2-A or presentation barrier. A run close in either separate transition-to-selection window uses P1-C `BetweenCourseEntries`: after Basic `Advanced` it closes the successor Practice and later Challenge reservations; after Practice `Advanced` it closes the retained Challenge reservation. Both prove the exact prior transition and no current selection/instance. The course and P2-B presentation contracts are admitted independently; their no-instance/no-request cases use the explicit success arms above rather than `NotApplicable`. P2-A alone uses `NotAdmitted` for the frozen `NotAdmittedBySnapshot` branch and uses the table's explicit success arms only for `Admitted`. Any nonzero hidden registry, unexpected reservation, work, domain, token, or callback turns the corresponding admitted-owner row into failure evidence.

## Restart and Retry Taxonomy

| Term | Scope | Result state | Revision-1 behavior |
|---|---|---|---|
| P1-E attempt retry | same Basic lesson | no stage result | new attempt ID/ordinal/generation after old attempt closure |
| Practice reset | same Practice entry | no stage result | unsupported |
| active-run restart | whole course before the shared P1-A latch selects `TerminalWon`/enters `TerminalFinalizing` | no stage result | snapshot-policy-gated restart from playable-stage entry |
| Fail Retry | committed Fail | immutable Fail result | P1-A typed action creates a new run |
| Clear Replay | committed Clear | immutable Clear result | P1-A typed action creates a new run |
| revive | active combat life state | distinct from restart/result action | unsupported by P2-A revision 1 |

### Canonical active-restart order

1. UI, course, or presentation submits a pure `ActiveRunRestartRequest` to P1-A before cleanup.
2. P1-A validates a policy-allowed active/pre-outcome state and the nested P2-A policy's reason/phase.
3. P1-A contends on the shared terminal-or-restart latch; only a restart winner enters `RestartClosing` and invalidates course/result/terminal selection authority, while an outcome winner rejects the restart without cleanup.
4. P1-A derives and seals the complete immutable `ResolvedActiveRunRestartDispatch` from the entry snapshot.
5. Only then does P1-A request P1-E/course, P1-C, P2-A, and P2-B cleanup barriers. P1-E either wins an as-yet-unpublished Basic close with a suppressed continuation under the restart authority, or returns the exact already-published Basic-authorized receipt as `ReusedPriorBasicClose`; the latter leaves suppression of the still-unconsumed course continuation to P2-B and never mutates P1-E evidence.
6. After every receipt/fault result is known, P1-A seals one `StageRunAbortRecord`.
7. Success follows `Aborted -> Disposed` and executes the already sealed dispatch.
8. Failure follows `Aborted -> ClosureFaulted`: no dispatch, no new run, no result/progress, no reopened latch, and no false Disposed claim.
9. Only successful target entry creates the new run/course/entry generations and selects Basic.

The restart dispatch carries its runtime-issued ID/canonical dispatch digest, the frozen P2-A semantic digest, optional course ID/revision/digest, and `restartCourseEntryId = Basic` provenance. The aggregate `StagePresentationQuiescenceReceipt` records that same dispatch ID/digest even if no presentation request is active; an active request's `StagePresentationResult` also echoes it. Neither is restart authority.

## Integration Boundaries

### P1-B spine

`PlayableStageDefinition` may add one optional `TutorialCourseDefinitionRef`. It does not copy lesson proof, scene paths, spawn fields, objective semantics, or player progress. Course binding/order/transition semantic changes affect the new-schema route digest and appropriate revisions.

### P1-A run/result

New-schema route snapshots include the course snapshot/digest. Result provenance may include the course ID/revision/digest and traversal coverage, never a mutable course-complete flag. Abort records may carry course closure-fault evidence. Active-restart dispatch is sealed before all cleanup.

### P1-C encounter

Practice and Challenge require exact separate course-scoped binding/execution generations under one agreeing `ProductTutorialCourseScope` or `IsolatedTutorialCourseFixtureScope`. The course, P1-C static plans, and P2-A set must carry the same product route or fixture ID/revision plus course identity; a product spine rejects every isolated arm. Practice additionally needs a bounded `NonTerminalPracticeActivity` binding; the current required-defeat sequence contract cannot be silently reused as no-proof Practice. P1-C gates are lifecycle inputs only, not Clear or mastery. Practice disposal must finish before Challenge activation, and the two bindings may not hold the scene lease concurrently.

### P1-D mastery/progress

P2-B reads one exact committed objective row. Basic completion, Practice exit, P2-A recommendation, variant purpose, and raw summon use are not mastery. P2-B cannot write `StageProgressState`, a prepared intent, an application record, or a save migration.

### P1-E lesson/attempt/reset

P1-E retains proof and gameplay-disposition authority. In a migrated P2-B cohort, its result continuation targets the exact course entry, disables legacy parallel advance, and carries a `FullyReleased` current-director course-ownership receipt with zero loans before Practice can become Available. Persistent lesson unlock and TutorialProgress remain absent.

### P2-A variability

The existing first P2-A product schema binds Story only, and its separate single-entry Practice/Challenge validation sets cannot be combined into a course. The isolated P2-B fixture requires one `IsolatedTutorialCourseFixtureScope` binding set selected in the sole `variantBindingSelection`, containing exactly two distinct entry-scoped members, Practice and Challenge, with agreeing course/P1-C fixture scope, scoped keys, variants, capabilities, and receipts. Product promotion replaces that with one separately reviewed `ProductTutorialCourseScope` set of the same bounded shape; neither scope coexists with the revision-1 Story-only product set unless another schema is reviewed. A completed pre-activation configuration receipt is distinct from the run-level P2-A quiescence receipt; the latter remains open until result/abort/restart closure unless a new entry-scoped lease is explicitly added.

### P2-B presentation

The course sends snapshotted presentation requests carrying the current sealed `CourseEntrySelection` runtime ID/canonical digest and matching course/session/entry generations; no course request may acquire a presentation domain without that authorization. The adapter owns only its acquired presentation domains. Course transition and canonical presentation-result digests are separate receipts. On post-result exit, P1-A seals `ResolvedTerminalActionSelection` before presentation restoration and the adapter only echoes that selection ID/digest; it cannot resolve, select, replace, or dispatch navigation. The current Station bridge and future adapter may not both restore time scale, HUD, input, or pointer state.
